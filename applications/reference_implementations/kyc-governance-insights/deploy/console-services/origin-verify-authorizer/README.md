# Origin-Verify Authorizer (API Consolidation — Phase 2)

Locks the KYC-exclusive backend HTTP APIs so they are reachable **only through CloudFront**,
closing the Phase 1 residual gap: the raw `*.execute-api.*` URLs were still directly hittable
with the publicly-known `x-api-key`.

## How it works

```
Browser ──(no secret)──▶ CloudFront /svc/*  ──inject x-origin-verify: <secret>──▶ console gateway ──▶ backend
                          (edge only)                                                                 │
                                                                        REQUEST authorizer checks ────┘
                                                                        x-origin-verify == secret
```

- The secret is injected **at CloudFront** (the authenticated edge) as an Origin Custom Header,
  so it never reaches the browser and is never in git or the JS bundle.
- Each of the 5 KYC-exclusive backends gets a shared HTTP-API **REQUEST authorizer** whose
  identity source is `$request.header.x-origin-verify`. Missing header → 401 (short-circuited by
  API Gateway); present-but-wrong → the Lambda returns `isAuthorized:false` → 403.
- Because the console gateway does **not** inject the secret, hitting the gateway directly is
  also rejected — only real browser→CF→gateway→backend traffic carries it.

## Rollback

```bash
bash phase2-rollback.sh          # detach authorizers + set routes back to NONE (non-destructive)
python3 phase2-cf-inject-header.py remove E1V1IBH8DIKFGR   # optional; harmless to leave
python3 phase2-cf-inject-header.py remove E1Q6VO2AHA03JB
```

Backends keep working through CloudFront after rollback (their in-Lambda `x-api-key` check
remains; CF still sends `x-api-key`).

## Secret handling (SECURITY.md-aligned)

- The secret is **generated by CloudFormation into AWS Secrets Manager** (`kyc/origin-verify`),
  encrypted at rest with the Secrets Manager KMS key. No human ever handles it; it is never in
  the template, an env var, git, or the browser.
- The authorizer Lambda reads it **at runtime** from Secrets Manager (env var holds only the
  ARN) and caches it in memory for 300s. Its role can read **only that one secret** (least
  privilege).
- The CloudFront `x-origin-verify` Origin Custom Header must carry the literal value (CloudFront
  cannot reference Secrets Manager). `phase2-cf-inject-header.py` fetches it from Secrets Manager
  and writes it directly into the distribution config — the value never appears on the command
  line or on disk (the transient CF config file is deleted immediately).

### Residual (documented, not a shortcut)
The header value is stored in the CloudFront distribution config, so it is plaintext-at-rest
**there** and readable by a principal with `cloudfront:GetDistributionConfig` on the dist. This is
inherent to using an origin custom header (the only alternative, Lambda@Edge fetching from Secrets
Manager per request, is disproportionate for this demo). It is gated by control-plane IAM and never
reaches the browser. Accepted for the demo; revisit if the threat model tightens.

### Rotation
```bash
# generate a new value in Secrets Manager, then re-push it to both dists:
aws secretsmanager rotate-secret --secret-id kyc/origin-verify        # or put-secret-value
python3 phase2-cf-inject-header.py add E1V1IBH8DIKFGR kyc/origin-verify
python3 phase2-cf-inject-header.py add E1Q6VO2AHA03JB kyc/origin-verify
```
The authorizer picks up the new value within its 300s cache TTL — no redeploy, no attach change.
Update CloudFront in the same window to avoid a brief mismatch.
